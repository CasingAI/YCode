# ZCode 富渲染输出规范

ZCode 客户端除了标准 Markdown，还能把某些标记渲染成更丰富的结构。本技能说明当前支持哪些标记、怎么写、以及什么时候该用。

当前只有**折叠区块**一种格式。不要自行发明别的标记语法（例如 `:::note`、`:::tip`、`<callout>`）——客户端不认，它们会原样显示成文本。

## 折叠区块

### 语法

用 HTML 原生的 `<details>` / `<summary>` 标签对：

```html
<details>
<summary>折叠标题</summary>

正文 markdown 内容。

</details>
```

客户端把这一对标签接管成一张可折叠卡片：默认收起，读者点标题展开。`<summary>` 的文本就是卡片上显示的标题。

### 写作规则

1. `<summary>` 必须是 `<details>` 的第一个子元素。放在其它位置，标题不会生效。
2. `<summary>` 与正文之间必须有一个空行。空行让正文被当作独立的块级 Markdown 解析；缺空行时正文会被并进标题所在的段落。
3. 默认收起。只有内容必须立刻可见时才写 `open` 属性（`<details open>`）。
4. `<summary>` 必须自包含。读者在收起状态下只看到标题，标题单独看也要能明白里面装的是什么。不要写「详情」「展开查看」「点击这里」这类没有信息量的标题。
5. 关键结论不要放进折叠块。折叠块用来装补充细节、逐条展开的分支、可选参考；读者需要立刻知道的结论留在正文。
6. 折叠区里的正文照常写 Markdown：列表、代码块、表格、引用都可以用。

### 判定步骤

写最终回答之前，按顺序判断下面三步。判定结果是硬要求，不是建议。

1. 回答里有没有 2 段以上可以独立读懂的支撑内容？每段自成一体，读者可能只想看其中一段。
   - 有 → 必须折叠这些段落，继续第 2 步。
   - 没有 → 不折叠，直接平铺输出。
2. 折叠之后，正文里还剩不剩下读者必须先看到的结论？
   - 剩 → 折叠。
   - 不剩 → 把结论提到正文，只折叠支撑细节。
3. 折叠块里是不是只有一两行？
   - 是 → 不折叠，直接写出来。
   - 否 → 折叠。

「可以独立读懂的支撑内容」指这些形态：

- 并列的观点、对比项、失败模式、可选方案，每项带自己的依据。
- 分步的步骤，步骤本身一句话，细节在后面。
- 实测数据表、日志、源码依据与文件位置。
- 事故复盘里的证据链。
- 可选参考与延伸阅读。

折叠不会丢内容。客户端把折叠块渲染成可展开的卡片，文字始终留在回答里，默认收起只是让正文更短。担心读者看不到内容不是不折叠的理由。

### 什么时候用

- **一组并列观点**，每一点都带展开才看得清的细节。例如三个可选方案的逐项利弊、三种失败模式的成因与规避方式。
- **分步骤的说明**，步骤本身很短，每步的展开细节可以后置。
- **可选内容**：参考资料、完整日志、扩展用法、延伸阅读。
- **实现细节**：改了哪几处、为什么这么改、放弃了哪些方案。

### 什么时候不用

- 回答本身就是一段话，或者结论就是要被立刻看到的内容。
- 折叠块里只有一两行。收起比展开更费事，直接写出来。
- 需要嵌套超过两层。深层折叠会让读者不断点开。
- 一条消息里超过 5 个折叠块。折叠块过多会让正文变成目录，读者要逐个点开才知道你说了什么。

### 示例

一组并列观点，每点带展开细节：

```html
<details>
<summary>三个可能造成重复写入的失败点</summary>

**并发写入冲突。** 两个写入者同时落到同一路径时，后写的覆盖先写的。规避方式：写入前先读一次当前版本号，版本不一致就重试。

**重试放大。** 首次请求其实已经成功，只是响应超时，重试又写了一遍。规避方式：重试请求携带幂等键，服务端按键去重。

**日志与指标错配。** 指标采集失败被吞掉，监控上看不出异常。规避方式：采集失败单独计数并设阈值告警。

</details>
```

分步说明，细节后置：

```html
<details>
<summary>迁移脚本的完整执行步骤</summary>

1. 备份数据库。
2. 运行 `pnpm migrate:up`，观察输出直到出现 `done`。
3. 校验行数与新表结构。
4. 关闭只读模式。

</details>
```

不使用的场景——直接平铺，读者一眼看到全部：

```text
缓存没生效有两个原因。第一个是键的生成用了请求时间戳，每次都不一样，命中不了；第二个是 TTL 设成了 0，等于不缓存。
```

调查结论报告——结论留在正文，证据与工程问题折叠：

```html
<details>
<summary>实测证据（2026-10-20，macOS arm64）</summary>

| 测试项 | 结果 |
|---|---|
| WebSocket 透传 | 握手 870ms，首包 1718ms，echo 正常 |
| 纯空闲连接 | 125.7 秒后被断开（code=1006） |
| 每 20s 发业务数据帧 | 存活 200s 无断开 |

</details>

<details>
<summary>必须解决的三个工程问题</summary>

1. **保活。** 空闲连接活不过 2 分钟，Web 端必须走应用层心跳。
2. **凭证传递。** token 走 URL query 会进访问日志和 Referer 头，需要重设计。
3. **边缘节点重启。** 官方文档明确会终止 WebSocket 连接，需要退避重连兜底。

</details>
```

不折叠的报告——结论只有两三行，支撑内容不超过一段：

```text
问题出在投影层：`usage` 的 patch 是整体替换 `usage` 对象，某一轮事件没带明细字段就等于把上一轮的明细清空。把 patch 改成字段级合并即可，新事件没带的字段保留上一轮的值。
```

## 扩展

本技能是富渲染格式规范的唯一载体。将来客户端支持新的富渲染格式（卡片等）时，规则会扩充到本文件，届时再按需使用。当前只写折叠区块。
