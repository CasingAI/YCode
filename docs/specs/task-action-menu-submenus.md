# Spec: 任务菜单的二级菜单折叠

## 目标

任务右键菜单和标题栏「⋯」下拉共用 `TaskActionMenuContent`。它最初有 11 行，把「复制路径 / 复制任务路径 / 复制日志路径 / 复制会话 ID」和「查看调用轨迹 / 反馈问题」这些低频诊断动作，与置顶、重命名、归档、标记未读这些主流程动作以完全相同的行权重平铺在一级。

本 spec 规定这些诊断动作如何折叠进二级菜单。折叠后一级菜单只承载主流程分组。

## 产品规则

### 一级菜单结构

```
置顶任务 / 取消置顶
重命名任务
归档任务 / 取消归档任务
标记为未读
在分屏打开            （仅桌面 shell 传入）
─────────────────
在 Finder 中打开      （手机远控窄屏隐藏）
─────────────────
复制信息 >
─────────────────
调试 >
```

「重新生成标题」由 `session-title-regeneration.md` 引入，收在「调试」子菜单内，不占一级行位。本 spec 只管它在结构里的位置，不管它的行为。

四个分组之间各有一条 `Separator`。

第三行的文案按归档态在「归档任务 / 取消归档任务」之间切换，行的位置、层级与分隔线数量不受影响；取值来源与交互规则见 `task-archive-membership-in-header-menu.md`。本 spec 只管菜单结构，不管这一行的文案。

### 分隔线规则

`Separator` 只在它两侧都有可见条目时渲染。条目被条件隐藏时，包围它的两条分隔线里必须跟着少一条，**一级菜单不允许出现两条相邻分隔线**——那是同一个分组边界被画了两遍，视觉上表现为条目之间多出一根横线。

因此窄视口（`hideMobileUnsupportedActions`，见「负面边界」）隐藏「在 Finder 中打开」后，一级菜单退化为：

```
置顶任务 / 取消置顶
重命名任务
归档任务 / 取消归档任务
标记为未读
─────────────────
复制信息 >
─────────────────
调试 >
```

两条分隔线。「标记为未读」与「复制信息」之间保留一条，它承担的是任务管理分组与诊断分组之间的边界，与「在 Finder 中打开」在不在场无关。

反过来也不加兜底：不为「自动折叠相邻分隔线」写通用 helper。会让分隔线变成孤儿的条件条目只有「在 Finder 中打开」——它是唯一一个独占一个分组、两侧都紧邻分隔线的条目。「在分屏打开」虽然也是条件渲染，但坐在有其他成员的任务管理分组里，消失后分组边界不变。规则由本节和回归测试共同守住。

### 「复制信息」子菜单

折叠对象是以下四项，出入子菜单时保持原有顺序、文案、`disabled` 条件、`title` 理由和 `onSelect` 回调，一行逻辑不改：

1. 复制路径
2. 复制任务路径
3. 复制日志路径
4. 复制会话 ID（仅 `onCopySessionId` 存在时渲染）

### 「调试」子菜单

折叠对象是三项，条件渲染规则不变，按此顺序：

1. 重新生成标题（仅 `onRegenerateTaskTitle` 存在时渲染；由 `session-title-regeneration.md` 引入）
2. 查看调用轨迹（仅 `onViewModelTrajectory` 存在时渲染）
3. 反馈问题（仅 `onOpenTaskFeedback` 存在时渲染）

「重新生成标题」排在最前：它是这三项里唯一会**改变**会话状态的（另两项只读），放在最前符合使用频率，也让「修复 → 查看轨迹 → 反馈」形成一条自然顺序。

外层条件是三者任一存在。只有一项存在时子菜单照样出现、里面只有一项——当前调用方都传全了三项，单项子菜单只是防御性分支，不为它再加一层「退化成平铺」的逻辑。

### 触发器的禁用规则

两个子菜单的 `SubTrigger` 规则相同：**只在 `disableTaskActions`（只读态）时禁用**，`title` 挂 `disabledReason`。

不跟随 `disableTaskTargetActions`，也不跟随 `!activeSessionId`。这两个条件只作用于子项：

- `disableTaskTargetActions` 由 header 的 `taskMenuMembershipLoading` 派生，此时「复制路径」仍可用、「复制会话 ID」不可用。触发器跟着禁用会出现「唯一可点的复制项点不到」。
- `!activeSessionId` 只禁用「查看调用轨迹」。

触发器若跟着子项的禁用条件走，子项的禁用理由就没有入口可以查了。只读态下全部子项禁用，触发器一并禁用是准确的，且和同级「在 Finder 中打开」的既有行为一致。

### 共用约束

任务右键和工作区标题栏「⋯」下拉共用同一份 `TaskActionMenuContent`，注入的只是渲染原语（`ContextMenuSub*` / `DropdownMenuSub*` 三件套）。两处入口必须同时折叠，不存在只改一处的中间态。

## 状态所有者与事件顺序

无新增状态。两个子菜单的开合都是 Radix 内部状态，不进 zcode store。

复制回调实现（`handleCopyText`、toast、剪贴板兜底）、轨迹查看（`useModelTrajectoryStore`）和反馈（`useFeedbackStore`）的调用链路一行不碰，本次只改菜单结构。

## 负面边界

- 分组任务列表右键菜单（`workspace-grouped-tasks/task-context-menu-content.tsx`）是独立实现，动作集也不同（有「移动到分组」子菜单、没有「查看调用轨迹」），**不参与本折叠**。
- 折叠后的诊断动作没有命令面板或快捷键入口——这是复制了 `sidebar-more-menu.md` 的同类取舍，有意识接受。
- 文件树的「复制路径」是另一条路径，不动。
- 「在 Finder 中打开」的隐藏口径不在本 spec 内：它由 `useIsNarrowViewport()` 决定，只在标题栏「⋯」下拉接线（`WorkspaceHeaderSections.tsx`）。任务列表右键菜单不传 `hideMobileUnsupportedActions`，该条目始终渲染。本 spec 只约束隐藏后分隔线怎么退让，不改判定本身。

## 验收

1. 侧边栏右键任意任务 → 一级菜单 8 行、三条分隔线，末尾是「调试」带右箭头；「复制信息」和「调试」各自展开后是上面列出的条目，顺序、文案、禁用态与折叠前完全一致。
2. 工作区标题栏点「⋯」→ 同一份结构，作用对象仍是当前激活任务。
3. 任务列表展开过程中（成员关系加载中）右键 → 两个子菜单都能展开；「复制路径」可点、其余复制项灰着；「调试」两项都灰着且悬停有理由。
4. 只读态右键 → 两个子菜单触发器都灰掉，悬停出禁用理由。
5. 逐个点各复制动作与两项诊断动作 → toast 文案、剪贴板内容、右侧轨迹侧栏、反馈带参行为均与折叠前一致。
6. 键盘可达：方向键能进入子菜单，Esc 能逐级退出。
7. 窄视口（≤768px）点标题栏「⋯」→ 「在 Finder 中打开」消失，「标记为未读」与「复制信息」之间只有一条分隔线、「复制信息」与「调试」之间一条，任意两两相邻的条目之间不出现连续两条分隔线。
8. 窄视口右键侧边栏任务 → 该条目仍在，三条分隔线，与场景 1 一致。
