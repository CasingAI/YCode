# Spec: 桌面应用菜单随界面变化

## 目标

macOS 的应用菜单栏原本是一份写死的静态模板：无论当前停在任务、文件还是设置，条目完全相同，用户找不到当前界面真正能做的事。同时「关闭窗口 ⌘W」会在任何界面都生效，误按就关掉整个窗口，正在运行的任务被硬杀。

本次改造把应用菜单对齐 VS Code 的心智：

- 顶层菜单位置与顺序恒定，**内部条目随当前界面增删**，而不是只把条目置灰；
- 菜单项的快捷键与设置里的快捷键表同源，用户改键后菜单提示同步变化；
- `⌘W` / `Ctrl+W` 只在文件编辑器界面生效，语义是「关闭当前编辑器」，不再有关闭窗口的回落。macOS、Windows、Linux 三个平台语义一致。

## 产品规则

### 顶层结构

顶层菜单恒定为：YCode（应用名）、文件、编辑、视图、窗口、帮助。位置与顺序不随界面变化。Windows / Linux 没有应用名菜单，其余顶层一致。

菜单在 macOS 上全局只有一份（`Menu.setApplicationMenu` 是应用级 API），因此菜单内容跟随**焦点窗口**的上下文。

### 无边框窗口的可见入口

- Windows / Linux 主窗口使用 `frame: false`，Electron 不绘制窗口内原生菜单栏；`autoHideMenuBar` 和 Alt 不构成可靠入口。
- Windows / Linux 的左上全局工具组提供独立的应用菜单按钮，位于侧栏切换按钮之后。按钮通过 `IPlatformService.executeDesktopCommand` 请求 Main 弹出已有应用菜单，不构建第二份菜单模板或业务状态。普通、最大化、全屏及任务 / 文件 / 设置界面共用该入口；无工作区的文件备用外壳和独立设置页同样复用该按钮，避免关闭最后一个工作区后又丢失入口。
- Main 使用发起命令的窗口显示菜单，并在弹出前应用该窗口的菜单上下文；已销毁的窗口或尚未建立的菜单不弹出。菜单条目的语言、快捷键、可用状态与 macOS 系统菜单共用现有来源。
- macOS 保留系统菜单栏（全屏显隐由 macOS 管理），Windows / Linux 使用应用菜单按钮；Desktop 文件主视图不重复渲染页内文件 / 编辑菜单。Web 不显示宿主应用菜单按钮，文件主视图提供可触摸的文件 / 编辑菜单，见 `workspace-files.md`。

```text
Windows / Linux 左上应用菜单按钮
  → IPlatformService.executeDesktopCommand(ShowApplicationMenu)
  → Main：应用来源窗口的上下文 → 弹出已有 Menu
  → 既有 DesktopCommand / UiCommand → 原所有者执行
```

### 文件菜单

| 条目       | 任务 / 设置界面 | 文件界面 | 快捷键 |
| ---------- | --------------- | -------- | ------ |
| 新建任务   | 有              | 有       | `⌘N`   |
| 新建文件   | 有              | 有       | `⌥⌘N`  |
| 打开工作区 | 有              | 有       | `⌘O`   |
| 保存       | 无              | 有       | `⌘S`   |
| 另存为…    | 无              | 有       | `⇧⌘S`  |
| 全部保存   | 无              | 有       | `⌥⌘S`  |
| 关闭编辑器 | 无              | 有       | `⌘W`   |

分隔线跟随其所属分组显隐，不得出现孤立分隔线。

「新建文件」在任何界面都可用：它新建未命名文件并切到文件界面，让新标签立刻可见。
其余文件专属条目（保存 / 另存为 / 全部保存 / 关闭编辑器）只在文件界面出现。

「关闭窗口」不属于文件菜单：它不读写文件，放在窗口菜单里更贴近它的作用对象。三个平台的文件菜单都只有「关闭编辑器」这一条关闭类条目。

### 编辑菜单

撤销、重做、剪切、复制、粘贴、全选在所有界面都存在。查找（`⌘F`）、查找替换（`⌥⌘F`）只在文件界面出现。

撤销 / 重做的作用对象由「操作发生前的编辑焦点」决定：焦点在代码编辑器时作用于编辑器，焦点在聊天输入框时作用于输入框。菜单点击会让网页失焦，因此必须记录失焦前的目标，不能只看点击瞬间的 `document.activeElement`。

「最近聚焦目标」由编辑目标注册表记录：聊天输入框拿到焦点时登记自己；代码编辑器登记句柄，并在 Monaco 报出焦点变化时更新登记。

### 窗口菜单

窗口菜单保留最小化、缩放、前置全部窗口（缩放与前置全部窗口只有 macOS 才有）。三个平台都提供「关闭窗口」，**不带快捷键**——`⌘W` / `Ctrl+W` 已经改为关闭编辑器，不再占用关闭窗口的键位。

### 关闭编辑器快捷键的语义（macOS / Windows / Linux 一致）

三个桌面平台规则完全相同，不按平台分叉：

- 任务、设置等非编辑器界面：菜单里不出现「关闭编辑器」，`⌘W` / `Ctrl+W` 不关闭任何标签、侧栏或窗口。
- 文件界面：菜单出现「关闭编辑器 `⌘W`」，按键或点击菜单只关闭当前聚焦编辑器组里的活动标签。
- 关闭最后一个标签后保留空编辑区与应用窗口，再次触发为空操作。
- 关闭编辑器不会关闭窗口，因此不会触发窗口关闭时对 Host / Agent 进程的清理，运行中的任务不受影响。
- 关闭编辑器不再经由侧栏标签：侧栏标签用它自己的关闭按钮关，关闭快捷键只对编辑器生效。

### 条目状态

条目在界面下根本不存在时**不出现**；存在但当下不可用时**置灰**：

- 文件界面没有可关闭的标签时，「关闭编辑器」置灰；
- 当前标签是图片等只读预览时，「保存 / 另存为 / 全部保存」置灰；
- 「全部保存」在没有未保存文件时置灰。

未命名文件（还没有路径）同样可以保存：保存动作转入另存为对话框，因此「保存 / 另存为」不置灰。

### 快捷键与菜单的关系

菜单上显示的快捷键来自快捷键设置表的用户覆盖，与设置页显示的键位一致；没有用户覆盖时取快捷键命令表里的默认绑定，菜单不自己写第二份键位。

保存、另存为、全部保存、新建文件、撤销、重做、查找、查找替换这些由渲染进程执行的命令，菜单项**只显示键位、不向系统注册**（`registerAccelerator: false`），实际按键由渲染进程的统一快捷键分发消费。这样菜单点击与按键走同一条实现路径，不会双触发。

各条目的键位来源：

| 菜单条目                            | 键位来源                                               |
| ----------------------------------- | ------------------------------------------------------ |
| 保存 / 另存为 / 全部保存 / 新建文件 | 快捷键命令表的同名命令（可改键）                       |
| 查找                                | `findInTask`（与「任务内查找」同一条命令，按界面分派） |
| 查找替换                            | `findReplaceInEditor`（可改键）                        |
| 撤销 / 重做                         | 快捷键命令表的「菜单展示固定键位」段落（固定不可改）   |

撤销 / 重做固定为 `⌘Z` / `⇧⌘Z`：`⌘Z` 由代码编辑器与聊天输入框的原生历史消费，渲染进程再拦截会与原生处理叠加成「一次按键撤两步」，因此它们不进可改键的快捷键表，只在菜单上展示键位。

新建任务、打开工作区、关闭编辑器、缩放这些由主进程执行的命令，菜单项照常向系统注册 accelerator。

### 隐藏条目的快捷键必须显式关闭

Electron 的 `acceleratorWorksWhenHidden` 默认是 `true`：条目被隐藏后，它的 accelerator **仍然会触发**。因此「关闭编辑器」这类「只在某个界面存在」的条目必须显式设置 `acceleratorWorksWhenHidden: false`，否则 `⌘W` 在任务界面仍会触发关闭编辑器。三个平台都按这条规则处理。

## Web 端与手机远控

Web 端没有宿主应用菜单，本 spec 的条目、显隐与置灰都不适用。边界如下：

- 桌面菜单上下文投影与渲染进程命令下发在 Web 端是空实现（`syncMenuContext` / `onExecuteUiCommand` 提供 no-op），界面切换不改变 Web 端的任何宿主行为。
- `⌘W` / `Ctrl+W` 在 Web 端保持浏览器语义（关闭浏览器标签页）。「关闭编辑器」只属于桌面端（macOS / Windows / Linux），Web 端不实现，也不回落为关窗口；因此设置页在 Web 端不展示这条命令。
- 保存、另存为、全部保存、新建文件、编辑器内查找替换走渲染进程的统一快捷键分发：桌面与 Web 行为一致，键位同样可在设置里改。
- `⌘F` 按界面分派的规则在 Web 端同样成立：任务界面查对话，文件界面交给代码编辑器自己的查找。
- Web 端的 `⌘N` / `⌘O` 由根级回退监听消费（menu 通道命令在 Web 端不可配置，见 `keyboard-shortcuts-settings.md`）。新增命令的默认键是 `⌥⌘N` / `⇧⌘S` / `⌥⌘S` / `⌥⌘F`，与这两个键不重叠，同键双动作不会发生。

## 状态所有者

| 状态                                 | 所有者                                 | 说明                     |
| ------------------------------------ | -------------------------------------- | ------------------------ |
| 打开的标签、正文、脏态、聚焦编辑器组 | 文件工作台 Store（`filesEditorStore`） | 菜单不持有文件事实       |
| 当前外壳主视图（任务 / 文件 / 设置） | `tabStore` 的主视图投影                | 菜单上下文的唯一来源     |
| 菜单上下文副本                       | 主进程按窗口缓存                       | 只是投影，不参与业务判断 |
| 应用菜单本身                         | 主进程 `Menu.setApplicationMenu`       | 全局一份，跟随焦点窗口   |

渲染进程把当前上下文投影给主进程：

```ts
interface DesktopMenuContext {
  view: "tasks" | "files" | "settings";
  editor: {
    hasActiveEditor: boolean;
    canSave: boolean;
    dirtyFileCount: number;
  } | null;
}
```

`editor` 只在 `view === "files"` 时非 null。

投影只包含菜单需要的布尔量与计数，不含文件正文。投影由标量组成：数组引用变化但内容没变（例如每次击键重建的 buffers）不得触发同步，否则每次按键都跨进程发一遍。

## 事件顺序

```text
用户切换外壳主视图 / 打开关闭文件 / 文件变脏
  → 渲染进程计算菜单上下文投影
  → 平台通道 SyncMenuContext（按窗口）
  → 主进程按窗口缓存投影
  → 主进程按焦点窗口的投影原地更新菜单条目的 visible / enabled

用户按 ⌘W / Ctrl+W（菜单 accelerator，主进程收到）
  → 主进程下发 CloseActiveContextRequest
  → 渲染进程派发「关闭当前编辑器」请求
       ├─ 文件界面：关闭当前聚焦编辑器的活动标签
       └─ 其它界面（任务 / 设置）：什么都不做
```

三个平台都不存在「关侧栏标签」或「关窗口」的回落分支。

菜单项点击与快捷键最终命中同一个渲染进程命令实现。

## 不变量

- 顶层菜单的顺序与位置恒定；界面切换不重建菜单，只原地改 `visible` / `enabled`。
- 菜单条目 id 稳定，跨界面切换不换 id。
- 菜单永远不持有文件正文或可写缓冲。
- 渲染进程侧的界面判断是最终依据；主进程缓存的上下文可能滞后，不得作为唯一门禁。
- 任何平台的任何关闭编辑器路径都不得调用 `CloseWindow`，不得触发窗口关闭时的进程清理。
- 菜单点击与快捷键命中同一个实现，单次操作只执行一次。
- 快捷键表是键位唯一事实来源；菜单不自行解析键位。
- 菜单上展示的键位必须是真实可用的键位：不存在「菜单显示但按下没反应」的条目。

## 负面边界

- 不新增「选择」「前往」等顶层菜单。
- 不做多窗口各自独立的菜单（macOS 平台限制）。
- 不给「关闭窗口」新增快捷键。
- 不保留「关闭侧栏标签」的快捷键路径：侧栏标签用它自己的关闭按钮关闭。
- 不做自动保存，也不挂没有实现方的菜单项（例如格式化文档）。
- 不把撤销 / 重做放进可改键的快捷键表（会与编辑器原生历史双触发）。
- 不改变窗口退出流程、任务生命周期与 Host / Agent 清理策略。
- 不改变 Desktop 与手机远控的会话与流式交付语义。

## 验收场景

1. 停在任务界面：文件菜单只有新建任务 / 新建文件 / 打开工作区；编辑菜单没有查找项；按 `⌘W` / `Ctrl+W` 什么也不发生，窗口与侧栏都不变。
2. 切到文件界面：文件菜单多出保存 / 另存为 / 全部保存 / 关闭编辑器；编辑菜单多出查找 / 查找替换。
3. 切到设置界面：条目回到任务界面的集合。
4. 文件界面下按 `⌘W` / `Ctrl+W`：只关闭当前聚焦编辑器组的活动标签；其它分屏的同名标签保持打开，未保存内容不丢。
5. 关闭最后一个标签：保留空编辑区，窗口仍在；再按 `⌘W` / `Ctrl+W` 无反应。
6. 菜单展开状态下切换界面：条目增删后没有孤立分隔线，菜单不闪烁。
7. 在设置里把保存改成 `⌘⇧S`：菜单上的保存提示随之变化，按 `⌘S` 不再保存。
8. 焦点在代码编辑器时点菜单「撤销」：撤销编辑器改动；焦点在聊天输入框时点菜单「撤销」：撤销输入框内容。
9. 两个窗口时：菜单跟随当前焦点窗口的界面。
10. 任务界面点菜单「新建文件」：新建未命名文件并切到文件界面，新标签可见。
11. 未命名文件：菜单里的「保存 / 另存为」不置灰，按 `⌘S` 转入另存为对话框。
12. 文件界面里编辑器持有焦点时按 `⌘F`：打开编辑器自带的查找（不是程序化再打开一次）。
13. Windows / Linux：文件菜单同样是「关闭编辑器 `Ctrl+W`」，窗口菜单提供不带快捷键的「关闭窗口」；任务界面按 `Ctrl+W` 不关窗口。
14. Web 端设置页里没有「关闭编辑器」这一行；Web 端按 `⌘W` 仍是浏览器语义。
15. 目标代码测试、`pnpm typecheck`、`pnpm lint`、`pnpm architecture:check --changed` 通过；不执行浏览器 / UI 自动化验收。
